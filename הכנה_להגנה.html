🛡️ CloudDrop — שאלות הגנה ותשובות

מסמך הכנה להגנה על הפרויקט. כל תשובה קשורה ישירות לקוד שלך. הקטעים בקוד מוצגים משמאל‑לימין כמו שצריך.

תוכן עניינים:
1. תקשורת וסוקטים  |  2. הצפנה ואבטחה  |  3. תהליכונים (Threads)  |  4. תכנות מונחה עצמים  |  5. בסיס נתונים  |  6. ארכיטקטורה וזרימה  |  7. שאלות מלכודת

1. תקשורת וסוקטים 🔌

ש: איך השרת והלקוח מתקשרים?
בניתי שרת TCP מבוסס סוקטים בעזרת מודול socket של פייתון. הלקוח פותח חיבור לשרת, שולח בקשה ומקבל תשובה. מעל זה יש שכבת הצפנה היברידית (RSA+AES).
ש: TCP או UDP? למה?
TCP. הוא מבטיח שכל הנתונים יגיעו, בשלמותם ובסדר הנכון — קריטי לקבצים (אם חצי PDF נאבד הוא לא ייפתח). זה נקבע בקוד: 
server_sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
AF_INET = IPv4, SOCK_STREAM = TCP. (אם היה SOCK_DGRAM זה היה UDP — "יורה ושוכח", בלי הבטחת הגעה.)
ש: איך השרת מטפל בכמה לקוחות בו זמנית?
לולאת השרת מקבלת חיבורים עם accept(), ולכל לקוח שמתחבר פותחת Thread נפרד. כך כמה לקוחות עובדים במקביל בלי לחסום זה את זה — זו הדרישה "שרת מרובה לקוחות". 
while True:
    client_sock, addr = server_sock.accept()   # ממתין ללקוח
    t = threading.Thread(target=handle_client,
                         args=(client_sock, addr), daemon=True)
    t.start()
ש: מה הפרוטוקול שתכננת? איך אתה יודע איפה הודעה נגמרת?
תכננתי פרוטוקול משלי: כל הודעה = 4 בתים שמציינים את האורך + גוף ב‑JSON. זה נחוץ כי TCP הוא זרם (stream) רציף בלי "גבולות הודעה" — בלי כותרת האורך הצד השני לא יודע איפה הודעה נגמרת והבאה מתחילה. קוראים קודם 4 בתים, יודעים את האורך N, ואז קוראים בדיוק N בתים. 
def send_message(sock, obj):
    body = json.dumps(obj).encode("utf-8")
    header = struct.pack(">I", len(body))  # אורך כ-4 בתים
    sock.sendall(header + body)
הגוף הוא {"command": "login", "data": {...}}.
ש: מה ההבדל בין הסוקט בצד השרת לסוקט בצד הלקוח?
שרת: bind() (תופס כתובת+פורט) → listen() (מתחיל להאזין) → accept() (מקבל לקוח). לקוח: רק connect() (מתחבר לכתובת+פורט של השרת).
ש: מה זה פורט, ומה המשמעות של 0.0.0.0?
פורט = מספר (אצלי 5000) שמזהה איזו אפליקציה במחשב מקבלת את החיבור. 0.0.0.0 אומר לשרת להאזין בכל כרטיסי הרשת — כך גם מחשבים אחרים ברשת יכולים להתחבר, ולא רק המחשב המקומי (שזה 127.0.0.1).
ש: כמה גדולה הודעה הפרוטוקול תומך?
כותרת האורך היא 4 בתים (">I" = unsigned int), כלומר עד 2³² ≈ 4 ג'יגה‑בייט להודעה. הקבצים מוגבלים ל‑50MB, אז בשפע.

2. הצפנה ואבטחה 🔐

ש: תסביר את ההצפנה ההיברידית. למה גם RSA וגם AES?
משלבים את היתרונות של שתיהן:
  • RSA (א‑סימטרי, מפתח ציבורי+פרטי) — בטוח להחלפת מפתח דרך רשת פתוחה, אבל איטי ולא מתאים לכמויות מידע גדולות.
  • AES (סימטרי, מפתח אחד) — מהיר מאוד, אבל צריך דרך בטוחה להעביר את המפתח.
הפתרון: משתמשים ב‑RSA רק כדי להעביר את מפתח ה‑AES בבטחה, ואז מצפינים את כל המידע עצמו עם AES המהיר.
ש: תאר את "לחיצת היד" (handshake) בתחילת חיבור.
1. הלקוח מבקש מהשרת את המפתח הציבורי RSA (פקודה public_key).
2. הלקוח מייצר מפתח AES אקראי, מצפין אותו עם המפתח הציבורי של השרת, ושולח (פקודה session_key).
3. השרת מפענח את מפתח ה‑AES עם המפתח הפרטי שלו ושומר אותו תחת session_token.
4. מכאן, נתונים רגישים (סיסמה בהתחברות) מוצפנים ב‑AES עם המפתח המשותף.
ש: איך נשמרות הסיסמאות בבסיס הנתונים? למה לא הצפנה?
הסיסמאות נשמרות כ‑hash עם bcrypt, לא בהצפנה ולא בטקסט גלוי. ההבדל: הצפנה הפיכה (אפשר לפענח), אבל hash הוא חד‑כיווני — אי אפשר לשחזר ממנו את הסיסמה. בהתחברות משווים את ה‑hash של מה שהוקלד ל‑hash השמור. גם אם מישהו גונב את ה‑DB, הוא לא מקבל את הסיסמאות. ל‑bcrypt יש גם salt מובנה — ערך אקראי שמתווסף לכל סיסמה כך ששתי סיסמאות זהות ייתנו hash שונה, ומונע מתקפות "טבלת קשת" (rainbow table).
ש: אילו פרצות אבטחה טיפלת בהן? (דרישת חובה!)
  • SQL Injection — כל השאילתות משתמשות ב‑parameterized queries (עם %s), כך שקלט המשתמש אף פעם לא מתערבב עם פקודת ה‑SQL.
  • סיסמאות — hash עם bcrypt + salt (לא נשמרות גלוי).
  • הצפנת תקשורת — RSA+AES על המידע הרגיש.
  • הגבלת גודל קובץ — תקרה כדי למנוע מתקפת מיצוי זיכרון.
  • תפוגת קבצים + הגבלת הורדות — קובץ נמחק אחרי זמן/מספר הורדות.
  • בקרת הרשאות — פעולות אדמין בודקות is_admin לפני ביצוע.
ש: מה זה SQL Injection ואיך מנעת אותו? תן דוגמה.
זו מתקפה שבה תוקף מכניס קוד SQL לתוך שדה קלט. אם הייתי בונה שאילתה עם חיבור מחרוזות ("... WHERE user='" + name + "'"), מישהו יכול להקליד ' OR '1'='1 ולעקוף. במקום, אני מעביר ערכים בנפרד והספרייה "מנקה" אותם: 
cur.execute("SELECT username FROM data WHERE username=%s", (rcv,))
ה‑%s הוא placeholder — הערך לעולם לא מתפרש כקוד SQL.

3. תהליכונים (Threads) 🧵

ש: מה זה Thread ולמה השתמשת בו?
Thread הוא "חוט ריצה" שמאפשר לבצע כמה דברים במקביל בתוך אותה תוכנית. השתמשתי בשני מקומות: (1) בשרת — Thread לכל לקוח, לתמיכה במרובה לקוחות. (2) בלקוח — כל פעולת רשת (התחברות, שליחת קובץ, רענון) רצה ב‑QThread נפרד, כדי שהממשק הגרפי לא ייתקע בזמן ההמתנה לשרת.
ש: מה ההבדל בין Thread ל‑Process?
Process = תוכנית עם זיכרון נפרד משלה. Thread = חוט ריצה בתוך תהליך, שחולק את אותו זיכרון עם שאר ה‑Threads. Threads קלים יותר ומהירים לתקשורת ביניהם, אבל צריך להיזהר מגישה מקבילה לאותו מידע.
ש: למה QThread ולא Thread רגיל בצד הלקוח?
ב‑PyQt אסור לעדכן את הממשק מ‑Thread שאינו הראשי. QThread + סיגנלים (pyqtSignal) מאפשרים לתהליך הרקע לסיים את העבודה ואז "להודיע" לממשק בבטחה לעדכן את עצמו. למשל self.done.emit(files) בסיום שליפת קבצים.
ש: איך אתה מתמודד עם גישה מקבילה (race conditions)?
כל Thread בשרת מטפל בלקוח שלו ומחזיק חיבור DB משלו. מילון ה‑sessions ב‑RAM מוגן בזכות ה‑GIL של פייתון (רק Thread אחד מריץ בייטקוד בכל רגע). בנוסף, כל בקשה היא קצרה ועצמאית.

4. תכנות מונחה עצמים 🧱

ש: כמה מחלקות יש לך? תן דוגמאות.
מעל 18 מחלקות. לדוגמה: Login, Home, SendFileWindow, PrintWindow, AdminWindow (חלונות), ומחלקות תהליכי רקע כמו HeartbeatThread, SendFileThread, DownloadFileThread, FetchFilesThread. (הדרישה: לפחות 4.)
ש: מה זה ירושה (Inheritance)? איפה השתמשת?
ירושה = מחלקה "יורשת" תכונות ממחלקה אחרת. כל החלונות שלי יורשים מ‑QMainWindow, וכל תהליכי הרקע יורשים מ‑QThread: 
class SendFileWindow(QMainWindow): ...
class HeartbeatThread(QThread): ...
כך אני מקבל "בחינם" את כל היכולות של חלון/תהליך, ומוסיף מעליהן את ההתנהגות שלי.
ש: מה זה __init__ ו‑self?
__init__ היא הבנאי (constructor) — רצה כשיוצרים אובייקט חדש מהמחלקה, ומאתחלת את המשתנים שלו. self הוא האובייקט עצמו — דרכו ניגשים לתכונות ולמתודות של אותו מופע ספציפי.
ש: מה זה pyqtSignal?
מנגנון "אות" של Qt לתקשורת בטוחה בין אובייקטים/תהליכים. למשל הגדרתי closed = pyqtSignal() בחלון השליחה, וכשהחלון נסגר הוא "פולט" את האות, וחלון הבית מקשיב לו וחוזר להופיע.

5. בסיס נתונים 🗄️

ש: באיזה בסיס נתונים השתמשת ומה הטבלאות?
MySQL. הטבלאות העיקריות: data (משתמשים, סיסמאות, is_admin, is_blocked), shared_files (קבצים משותפים, תפוגה, מונה הורדות), history (לוג פעולות), print_jobs (עבודות הדפסה), system_settings (הגדרות).
ש: מה זה PRIMARY KEY ו‑AUTO_INCREMENT?
PRIMARY KEY = מזהה ייחודי לכל שורה בטבלה (אין שניים זהים). AUTO_INCREMENT = הערך עולה אוטומטית ב‑1 לכל שורה חדשה, כך שלא צריך לנהל ידנית מזהים.
ש: למה הפרדת את ה‑DB לשרת ולא חיברת את הלקוח ישירות?
אם הלקוח היה מתחבר ישירות ל‑MySQL, סיסמת ה‑DB הייתה חייבת להיות בתוך אפליקציית הלקוח — פרצת אבטחה ענקית. השרת הוא "מתווך" בטוח: רק הוא מכיר את ה‑DB, והלקוח מדבר רק איתו, דרך פרוטוקול מוגדר ומוצפן.

6. ארכיטקטורה וזרימה 🏗️

ש: תאר מה קורה מרגע שמשתמש שולח קובץ ועד שהנמען מוריד אותו.
1. הלקוח מצפין את הקובץ עם מפתח AES חדש שנוצר לקובץ.
2. את מפתח ה‑AES הזה הוא מצפין עם המפתח הציבורי RSA של השרת.
3. שולח לשרת (פקודה upload_file): הקובץ המוצפן + המפתח המוצפן + נמענים + תפוגה.
4. השרת מעלה את הקובץ ל‑Supabase Storage ושומר רשומה ב‑MySQL לכל נמען.
5. הנמען מבקש את הקובץ (get_file); השרת מפענח את מפתח ה‑AES עם המפתח הפרטי שלו ומחזיר אותו יחד עם הקובץ.
6. הלקוח של הנמען מפענח את הקובץ עם ה‑AES ושומר אותו.
ש: מה זה Supabase ולמה השתמשת בו?
שירות אחסון בענן (Storage). הקבצים עצמם נשמרים שם ולא בתוך בסיס הנתונים — כך ה‑DB נשאר קל ומהיר ומחזיק רק מטא‑דאטה (מי שלח, למי, מתי פג).
ש: למה ארכיטקטורת לקוח‑שרת ולא הכל במחשב אחד?
כדי שכמה משתמשים על מחשבים שונים יוכלו לשתף קבצים ביניהם דרך נקודה מרכזית אחת (השרת), שמנהלת את המשתמשים, ההרשאות והקבצים בצורה מאובטחת ומרוכזת.

7. שאלות "מלכודת" נפוצות ⚠️

ש: למה יש בפרויקט גם Werkzeug אם אתה לא משתמש ב‑Flask?
משתמש בו רק בפונקציה אחת — secure_filename — שמנקה שמות קבצים מסוכנים בהעלאה (מונעת מתקפות path traversal כמו ../../). זו ספריית עזר, לא שרת אינטרנט.
ש: יש לך גם socket למדפסת — איך זה קשור?
זו דוגמה נוספת לשליטה בסוקטים: הדפסה ברשת דרך TCP socket לפורט 9100 (פרוטוקול JetDirect). זה בנוסף לתקשורת לקוח‑שרת הראשית שגם היא מבוססת סוקטים.
ש: מה קורה אם השרת קורס באמצע העברת קובץ?
TCP יזהה שהחיבור נקטע, והלקוח יקבל שגיאת חיבור (תפסתי אותה ב‑try/except והצגתי הודעה למשתמש). הקובץ לא "נתקע למחצה" ב‑DB כי הרשומה נכתבת רק אחרי העלאה מוצלחת.
ש: איך הוכחת שזה באמת מרובה לקוחות?
אפשר להריץ שני לקוחות בו זמנית (משני מחשבים או שתי הרצות) — שניהם מתחברים, נכנסים ושולחים קבצים במקביל, כי השרת פותח Thread לכל אחד.
💡 טיפ להגנה: אם שואלים שאלה שאתה לא בטוח בה — אל תמציא. תגיד "אני אראה לך בקוד" ותפתח את הקובץ הרלוונטי. השליטה בקוד שלך שווה יותר משינון.
